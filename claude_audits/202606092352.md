## 1. What this repository is (purpose)

GlobalGrid2050 is **not a normal static website**. It is a founder-controlled **energy-infrastructure intelligence platform** — described in its own doctrine as a *“Serverless Spatial Digital Twin and Constraint-First Design Engine.”* It codifies ~two decades of physical engineering experience into a browser-based spatial reasoning system.

Governing principle (stated repeatedly across the docs): **early constraint visibility prevents late-stage engineering failure.** Infrastructure projects fail when land, grid, cable routes, losses, access, substations, revenue and delivery risk are analysed separately. The platform brings those assumptions into one spatial + technical + financial environment for *screening and documentation* — explicitly **not** a replacement for qualified engineers, grid operators or statutory authorities.

It is deployed as a **GitHub Pages + Jekyll static site** with a custom domain (`CNAME` present), doing all geospatial, engineering and financial work **client-side in the browser** (no app server, no database, no backend). Licence: **CERN OHL S v2** (strongly reciprocal); binding text in `LICENSE.txt`.

## 2. Deployment & governance model (the working order)

This is the most important section to preserve, because the repo’s safety depends on it.

**The operating loop (from `AI_START_HERE.md` / `OPERATOR_MANUAL_V1.md`):**

1. Maintainer (Vikram) states strategic intent.
1. AI inspects the repo and proposes one small change.
1. AI creates the appropriate script, manifest, workflow or documentation.
1. Maintainer **manually triggers** the GitHub workflow.
1. **GridBot** executes through GitHub Actions.
1. GitHub records the commit; GitHub Pages redeploys.
1. Maintainer tests the live page and approves or rejects.

**Critical authority rule:** GridBot authentication (`GRIDBOT_PAT`) is *technical access, not human approval*. AI must never assume permission to deploy automatically, and must never trigger workflows on the maintainer’s behalf unless explicitly told to.

**GridBot has two distinct roles — do not conflate them:**

- **Role 1 — authorised GitHub automation identity.** For live data + file-generation pipelines (UK energy, electricity prices, carbon intensity, oil/fuel prices, metals, FX, EV-charging indexes, JSON feeds, markdown reports). Pattern: `scripts/<pipeline>.py` + `.github/workflows/<pipeline>.yml`, checkout via `GRIDBOT_PAT`, run Python, commit exact output files, push to `main` as GridBot.
- **Role 2 — old GridBot Feature Installer.** For controlled *app patches* (GIS SLD structural changes, scoped UI changes). Pattern: `feature_requests/<name>/manifest.yml` + `scripts/gridbot_feature_installer.py` + `.github/workflows/gridbot-feature-install.yml`, producing an install report.
- Data feeds → Role 1. App patches → Role 2. Never the reverse.

**LAUNCH FREEZE is currently in force** (`LAUNCH_FREEZE.md`). Governing rule: *“Freeze structure. Fix function. Document risks. Clean later.”* Until launch completes, do NOT: delete working version folders; move shared datasets/GeoJSON paths; archive/remove workflows; rename live app folders; perform Git LFS migration or history rewriting; mass-refactor large HTML/CSS/JS for appearance. Allowed: fix broken references, add documentation, add guardrails (e.g. `.gitignore`), patch visible functional defects, add non-destructive inventories. **Old versions are retained intentionally as rollback references — “safety memory,” not clutter.**

## 3. Architecture (Ventus OS Modular Pipeline)

Operating model: *human origin, AI reasoning, Python processing, YAML instruction, GitHub execution.* Built on shared cores (`ventus-core.js`, `ventus.css` at root; per-version engines like `repd_grid_atlasv8/ventus-corev8engine.js` + `ventusv8.css`), Python ETL, GitHub Actions, feature manifests, GridBot, and **versioned application “cartridges.”**

Standing doctrine (`ARCHITECTURE.md`):

- **Respect the geometry** — all engineering calculations use geodesic metres via Haversine; casual screen-pixel geometry must not silently replace it.
- **Defend the browser** — scale horizontally with regional HTML cartridges, modular assets, pre-processed data; don’t overload the client.
- **Defend the repository** — use Python/YAML/Actions for repeatable large-file operations; don’t hand-copy large code blocks into production.
- **Build forward, do not simplify** — large is acceptable if structured, versioned, testable, modular and maintainable.
- Long-context AI is an *amplifier, not a substitute* for architecture, deterministic scripts, version control, validation, rollback and human review.

Client-side stack: **Leaflet.js** (mapping/clustering), **Proj4js** (OSGB36→WGS84 transform, screening-grade only), **PapaParse** (CSV ingestion), **DataTables** (filter/paginate/search). The GIS SLD flagship additionally uses **MapLibre GL 3.6.2** and **Turf.js 6** from CDNs.

Scale of the system: **216 Python scripts**, **179 GitHub workflows**, **53 top-level GeoJSON** datasets, and the many versioned apps below.

## 5. The data spine & generation tracker (current state, verified today)

This is the most actively-changing subsystem and the one most likely to be mid-flight if something breaks.

**FUELHH confirmed spine — COMPLETE.** `data/generation/fuelhh_halfhourly/` holds **125 monthly CSV shards, 2016-01 → 2026-05**, fetched from Elexon BMRS **FUELHH** (settled half-hourly, transmission-metered). `BACKFILL_PROGRESS.json` shows `complete: true`, zero failed months. Each shard ~627–778 KB (well under the 25 MB discipline); ~93 MB total. Row schema: `{time (UTC), technology, generationMW, source="Elexon BMRS FUELHH"}`. Built by `scripts/backfill_generation_fuelhh_halfhourly_all_months_v6.py` via `.github/workflows/backfill_generation_fuelhh_halfhourly_v6.yml` (resumable, throttled, time-budgeted, dispatch + cron, directory-staged commit).

**Daily MW spine — built, CANDIDATE.** `data/confirmed/generation_daily_mw_spine_fuelhh_candidate.json` (~14.1 MB), per-`(date, technology)` `averageMW`/`highMW`/`lowMW` + `highAtUTC`/`lowAtUTC` + `completeness` + `status: candidate`. Built by `scripts/build_generation_daily_mw_spine_from_fuelhh.py`.

**Solar — layered from PVLive (CORRECT architecture, partial coverage).** FUELHH carries **no solar** (solar is embedded/distribution-connected, not a FUELHH fuel type) — verified: the FUELHH spine has **zero** Solar rows, which is correct. Solar is supplied separately from **Sheffield Solar PVLive**: `pvlive_solar_daily_browser.json` and `pvlive_solar_recent_30d_30min_browser.json`, stamped `source: "Sheffield Solar PVLive"`, `methodState: "PVLIVE EMBEDDED ESTIMATE"`, `status: candidate`. **Coverage is recent-only (from ~2026-05-10), NOT the full decade.**

**Browser wiring** (`uk_energy_tracking_v6/generation_history/live-config.js`): `dailyHistory` → the FUELHH daily spine; `recentHalfHourly` → `generation_recent_30d_30min.json`; `recentEcg` → `generation_ecg_all_technologies_30d_30min_candidate.json`; `solarDaily` / `solarRecentHalfHourly` → the PVLive files; fallbacks to the older `elexon_generation_sources_*` (FUELINST-era). Renderer reads `{date, technology, averageMW}` (daily) / `{time, technology, generationMW}` (half-hourly).

**Independent verification status:** the conventional transmission-connected buckets (coal, nuclear, gas/CCGT, OCGT, oil, pumped storage, biomass post-Nov-2017, transmission wind) are corroborated against DUKES 2025 Ch5, Ember, NESO/Elexon, Drax Electric Insights, EDF and the World Nuclear Association, and are citation-grade. Spot values verified to reproduce exactly from the shards: Coal high 10,776.5 MW (27 Feb 2018, “Beast from the East”), Coal low 0.0 MW (1 Oct 2017), Nuclear high 8,830.5 MW (5 Sep 2016), Nuclear low 2,196.5 MW (23 May 2026), Nuclear mean 5,473 MW / Coal mean 813 MW. **Must always be footnoted:** Solar is structurally absent from FUELHH, and total Wind is undercounted (embedded wind ~6.5 GW excluded). Reconcile any national-total claim against DUKES Table 5.1 / Chapter 6, Ember, NESO embedded forecast, carbonintensity.org.uk `/generation`, and PV_Live.

**Data-science doctrine** lives in `data_science_protocol/` — canonical: `THE_DATA_SPINE.md` (grain discipline: store the right grain; FUELHH=settled/confirmed, FUELINST=live/provisional; sums roll up, peaks do not; solar provenance-stamped; never overwrite good data; commit facts, regenerate bulk), stamped into `ARCHITECTURE.md`, `PHILOSOPHY.md`, `DATA_STORAGE_DISCIPLINE_PROTOCOL.md` and the V6 integrity protocol. The never-overwrite guard is implemented in `scripts/backfill_generation_aggregates_year_v6.py` (`should_replace_existing` / `weak_row`). A CI size guard (`.github/scripts/size_guard.sh` + `repo_guard.yml`) warns at 5 MiB / fails at 25 MiB on changed files.

## 6. Data layer & sources

Top-level GeoJSON (53 files) covers grid lines (11 kV → 400 kV), substations, power plants, roads, railways, ports, airports, data centres, EV chargers, emitters, subsea cables and more. **Largest files (GIS basemaps) are heavy and known:** `uk_primary_roads.geojson` ~76 MB, `uk_trunk_roads.geojson` ~64 MB, `uk_mainline_railways.geojson` ~52 MB (these exceed GitHub’s 50 MiB warning and are the bulk of repo weight; their eviction is a *post-launch* task, not done yet).

Primary public sources: Renewable Energy Planning Database (REPD); OpenStreetMap via Overpass API; Elexon BMRS (FUELHH/FUELINST); Carbon Intensity API; Sheffield Solar PVLive; ONS energy data; commodity/FX/market feeds. Third-party licences must be respected and labelled. Public source data is for screening/documentation, not validated operational truth.

## 7. Known pending items & risks (as of this snapshot)

None of these block the live site; they are the open tail from recent audits.

1. **Daily spine not slimmed** — `dailyHistory` points the browser at the ~14.1 MB full-provenance spine. A slim `{date, technology, averageMW}` derivative (~1–3 MB) is recommended for a smooth UI; not yet built.
1. **Solar history not backfilled** — PVLive solar is recent-only (from ~2026-05-10). Long-range (2016–2025) solar is still absent; backfill from PV_Live (history exists to ~2014) to close the caveat.
1. **Legacy generation files still tracked** — the old 14 MB `generation_recent_halfhourly_30d.json` and a duplicate Elexon CSV (`elexon_generation_sources_2026.csv` ≡ `_half_hourly.csv`) remain in the tree; untrack after confirming nothing reads them.
1. **`totalDaily()` peak summing** — sums per-technology highs/lows for the “All” view (non-additive); currently *not* rendered by the chart, so latent rather than visible.
1. **Workflow clutter** — 179 workflows, not yet classified per `WORKFLOW_REGISTRY.md`; preservation is the correct default during freeze.
1. **GIS basemaps (~190 MB) and history rewrite** — deliberately deferred to post-launch under the freeze.
