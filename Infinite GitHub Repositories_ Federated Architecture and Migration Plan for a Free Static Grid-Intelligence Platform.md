# Infinite GitHub Repositories: A Federated Architecture and Migration Plan for a Free, Static Grid-Intelligence Platform

## TL;DR

- **Adopt a polyrepo “hub-and-spoke” federation** built entirely on GitHub-native, free-to-host primitives: one **website/index repo** (the UI shell + landing page), a machine-readable **master contents index** (JSON, generated by CI), many **self-contained per-app repos** (each spun from a template repo with all client-side libraries vendored in), and a small number of **dedicated data repos**. The origin `globalgrid2050` (“whorl”) repo is treated as a read-only canonical source and is never pushed to — every extraction works from a fresh clone.
- **Respect the hard GitHub limits that shape the whole design.** Per GitHub Docs: “Published GitHub Pages sites may be no larger than 1 GB. GitHub Pages deployments will timeout if they take longer than 10 minutes. GitHub Pages sites have a soft bandwidth limit of 100 GB per month. GitHub Pages sites have a soft limit of 10 builds per hour.”  Git LFS free tier is only 1 GiB storage + 1 GiB/month bandwidth (metered overage thereafter at $0.07/GB stored and $0.0875/GB downloaded). These caps are exactly why a 2 GB monolith must be split, and why the heaviest geospatial data should be pre-tiled (PMTiles/vector tiles) or served as compact pre-computed JSON rather than shipped raw.
- **Extract with history using `git filter-repo`** (the Git-endorsed tool), wire every repo into the index via a scheduled/`repository_dispatch`-driven **index-builder workflow**, and preserve the existing audit-first GridBot doctrine by keeping the `workflow_dispatch` + audit-report-commit pattern in each repo plus a federation-wide consistency check. **One decision-critical caveat flagged up front:** per the Protomaps documentation, “PMTiles archives hosted on GitHub Pages currently do not load in Firefox,” so vector-tile archives must be hosted on a Range-friendly object store, not on Pages.

## Key Findings

1. **`git filter-repo` is the correct, history-preserving extraction tool, and it is inherently safe for the “leave origin untouched” constraint.** Every authoritative write-up (including the Netlify Developers guide and CoreUI guide) instructs you to *clone first, then rewrite the clone* — `filter-repo` operates only on the fresh clone, so the origin is never modified. The CoreUI guide states the result plainly: “After the split, the new repository is self-contained. The original monorepo is unchanged — you cloned it before running filter-repo.”  Git’s own documentation endorses `filter-repo` over the older `filter-branch`.  `git subtree split` is a viable lighter-weight alternative for a single clean subdirectory, but it is slow on large histories (a documented case at Close with 34,000 commits took “over 12 minutes”)  and handles only one branch and one directory at a time.
1. **The master index should follow the proven “Git repository as a generated index” registry pattern.** Cargo’s crates.io-index, RubyGems’ compact index, the Windows Package Manager (`winget-pkgs`) catalog, and community registries like `hermes-registry` all converge on the same design: a version-controlled repo where a machine-readable index file is **generated by CI, never hand-edited**, so it cannot drift from reality. As the hermes-registry documentation puts it: “index.json is generated, never hand-edited — CI regenerates it on every change so it can’t drift from the folders.”  That index even uses the exact fields this platform needs — `schemaVersion`, a `generated` timestamp, and per-entry `id`, `type`, `version`, `path`, `checksum`, and `compatibility`. (Note: the git-index model “doesn’t scale indefinitely; Cargo had to add a sparse index”  — relevant only at extreme scale, far beyond this platform’s needs.)
1. **Self-contained “all dependencies pre-installed” repos are best realized through GitHub template repositories plus vendored libraries.** Per GitHub Docs, a template repo lets anyone “Use this template” to generate a new repo where “a repository created from a template starts with a single commit” — unlike a fork, which “includes the entire commit history of the parent repository.”  Vendoring the client-side libs (Leaflet, MapLibre, Proj4js, PapaParse, Turf, DataTables) into each repo — rather than hot-linking a CDN — guarantees reproducibility and immunity to CDN outages. Industry guidance frames the tradeoff precisely: “Self-host or bundle: critical runtime libraries, strict privacy/compliance requirements… or when you require complete control over availability and performance.”  The one downside (staleness) is mitigated by Dependabot, which Chromatic notes keeps dependencies current versus “a hard-coded CDN URL that includes the version number, where version upgrades can only happen manually and thus tend to get stale.” 
1. **Multi-repo GitHub Pages hosting works cleanly via project sites under one custom domain.** Per GitHub Docs: “if you set a custom domain for a user site or organization site, that same custom domain will be used for all project sites owned by the same account”  — so each app repo is served at `domain/<repo-name>`. Only one repository at a time can own a given custom domain (“we enforce the unicity”),  so true per-app *subdomains* require separate CNAMEs. The pragmatic federation model is a **hub-and-spoke link model**: the index repo is the hub at the apex/root, and each app repo is a spoke at `domain/<app>`. Iframes and client-side routing are options but add fragility; plain hyperlinks/redirects are the most robust.
1. **Large geospatial data must leave the “raw GeoJSON in the app repo” pattern.** The right tools are PMTiles (described by Protomaps as “a single-file archive format for tiled data… low-cost, zero-maintenance map applications that are ‘serverless’”)   for map layers, served via HTTP Range requests, and compact pre-computed JSON/JSONL “facts” for tabular data. **Critical constraint:** GitHub Pages does not reliably serve Range requests for `.pmtiles` in Firefox. The Protomaps maintainer (GitHub user `bdon`) reproduced it — “I can reproduce it on <https://pmtiles.io/examples/maplibre.html> with stock Firefox which is bad”  — and the official docs carry the warning “PMTiles archives hosted on GitHub Pages currently do not load in Firefox.”  Git LFS is also a poor fit for serving data to browsers: GitHub Pages does not serve LFS files directly, and the free LFS tier (1 GiB storage / 1 GiB monthly bandwidth) is exhausted almost instantly by public traffic.
1. **Cross-repo consistency is achievable with GitHub Actions alone.** `repository_dispatch` (a webhook POST to `/repos/:owner/:repo/dispatches` with a `client_payload`)  lets a child repo notify the index repo on every release; a scheduled workflow plus the GitHub REST/GraphQL API (`/orgs/{org}/repos`, paginated at a maximum of 100 per page, or `gh repo list`/Octokit auto-pagination) lets the index-builder enumerate all org repos and rebuild the master index even if a child forgets to notify. This preserves the audit-first doctrine because the index rebuild can itself emit a committed Markdown+JSON audit report.
1. **Governance at “infinite” scale depends on naming conventions, templates, and automation — not heroics.** GitHub’s own Well-Architected guidance stresses, for polyrepos, “clear and consistent naming conventions and directory structures across repositories to maintain coherence.” The risk that polyrepos “split too finely” and make cross-cutting changes painful is real and well-documented (Joel Parker Henderson: “often organizations end up splitting things too finely, and now I’m unable to make a single commit to introduce a feature because my changes have to live across several repositories”);  the mitigations are a strict repo-type taxonomy, prefix-based naming, template repos so every new repo is born consistent, and `gh repo create --template` automation for spin-up.

## Details

### (a) Target Architecture: the “Infinite Repositories” Model

The federation is a **hub-and-spoke polyrepo** with four repo types. Every repo is public (required for free GitHub Pages on personal/free-org accounts) and independently deployable.

**Repo-type taxonomy:**

|Type                              |Naming convention                |Role                                                                                                                                                                                             |Pages?                         |Example                  |
|----------------------------------|---------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------|-------------------------|
|**Index/Website repo** (“the hub”)|`<org>.github.io` or `grid-index`|The UI shell, landing page, global search/registry browser. Hosts the human-facing catalog and the generated `index.json`. Federates all spokes via links/redirects.                             |Yes (apex/root + custom domain)|serves `/`               |
|**App repo** (“a spoke”)          |`app-<slug>-v<major>`            |One self-contained interactive application (e.g. `app-solar-bess-topology-v8`). All JS libs vendored, all small data bundled or fetched from a data repo/object store.                           |Yes (`domain/app-<slug>-v8`)   |the SLD Financial Sandbox|
|**Data repo**                     |`data-<domain>`                  |Versioned datasets shared across apps (e.g. `data-grid-networks`, `data-repd`, `data-context-layers`). Holds pre-tiled PMTiles pointers/compact JSON; raw sources optionally via LFS or Releases.|Optionally (compact facts only)|the GeoJSON spine        |
|**Template repo**                 |`template-app`, `template-data`  |Blueprints with dependencies pre-installed, CI workflows, audit scaffolding, and a manifest stub. New repos are generated from these.                                                            |No (blueprint only)            |—                        |

**How they interconnect:** The **master contents index** (`index.json` in the hub) is the single source of truth that maps every repo to its use-case, data dependencies, library versions, deployed Pages URL, version, and status. The hub’s UI reads `index.json` at runtime to render the catalog and link out to each spoke. App repos declare their data dependencies by name/version; data repos publish their datasets and a small `dataset.json` descriptor. The index is **generated**, not hand-maintained, by an index-builder workflow that enumerates org repos and reads each repo’s committed `app.json`/`dataset.json` manifest.

```
                    ┌─────────────────────────────┐
                    │  Hub: <org>.github.io        │
                    │  • UI shell / landing page   │
                    │  • index.json (generated)    │
                    │  • index-builder workflow    │
                    └───────────┬─────────────────┘
            links/redirects     │ enumerates + reads manifests
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
  app-…-v8 (Pages)        app-…-v6 (Pages)        app-price-est (Pages)
        │                       │                       │
        └─────────── fetch datasets by name/version ────┘
                                ▼
        data-grid-networks · data-repd · data-context-layers
        (compact JSON on Pages; PMTiles on R2; raw via LFS/Releases)
```

### (b) Migration Plan (origin repo never touched)

**Guiding safety rule:** every operation begins with `git clone https://github.com/ventusltd/globalgrid2050 <fresh-dir>`. No remote named `origin` pointing at the source is ever pushed to. `git filter-repo` only rewrites the local clone; the source is unchanged by construction. As a belt-and-braces measure, first create a **mirror backup** (`git clone --mirror`) stored in a separate `archive-whorl-mirror` repo so the canonical state is snapshotted before any work.

**Phase 0 — Inventory & freeze (rollback: none needed; read-only).**

- Clone the whorl repo once. Generate a manifest of every app, dataset, and document with paths and sizes (the partially-complete master contents file and the size-governance report are the starting point).
- Decide the repo split list and naming (e.g. `app-solar-bess-topology-v8`, `data-grid-networks`). Define the index schema (section c) and the template repos (section d) before extracting anything.
- **Benchmark to advance:** a complete split-list + naming map + schema agreed.

**Phase 1 — Stand up scaffolding (rollback: delete the new empty repos).**

- Create the org (if not already), the hub repo (`<org>.github.io`), `template-app`, and `template-data`. Mark the templates as template repositories (Settings → Template repository).
- Configure the custom domain on the hub so all future project sites inherit `domain/<repo>`.
- **Benchmark:** hub serves a placeholder page at the custom domain; “Use this template” produces a working empty app.

**Phase 2 — Extract data repos first (rollback: delete the data repo; origin untouched).**

- For each dataset directory, in a fresh clone run `git filter-repo --path <dir>/ --path-rename <dir>/:` to extract with history, then push to a new `data-<domain>` repo.
- Convert heavy GeoJSON to PMTiles/vector tiles and pre-compute compact JSON facts; commit compact artifacts, move raw/oversized sources to LFS or GitHub Releases, and (for PMTiles) upload to a Range-friendly object store.
- Add a `dataset.json` descriptor and the audit-first workflow.
- **Benchmark:** each data repo is < 1 GB, builds in < 10 min, and serves its compact facts.

**Phase 3 — Extract app repos (rollback: delete the app repo).**

- For each app/version directory, `git filter-repo` the subtree into a repo generated from `template-app` (or push the filtered history then layer the template files on top). Vendor the libraries, point data fetches at the data repos/object store, and add the `app.json` manifest.
- Enable Pages per repo. Verify the live site at `domain/app-<slug>-v<major>`.
- **Benchmark:** each app loads and functions identically to its monolith counterpart (test in Chrome **and** Firefox).

**Phase 4 — Build the master index (rollback: revert index commit).**

- Add the index-builder workflow to the hub. Run it to enumerate all org repos, read each manifest, and generate `index.json`. Build the catalog UI on top.
- **Benchmark:** `index.json` lists every repo with correct URLs, versions, and dependencies; the hub UI links to every spoke.

**Phase 5 — Wire automation & cutover (rollback: index/UI is additive; spokes already live).**

- Add `repository_dispatch` notifications from each child to the hub; add the scheduled nightly index rebuild; add the federation consistency check.
- Announce the hub as the canonical entry point. The whorl repo remains live and untouched as the archived source.
- **Benchmark:** a new repo created from `template-app` appears in `index.json` automatically within one scheduled cycle.

### (c) Master Contents Index Schema

A generated, append-friendly JSON document (YAML is equivalent if preferred). Designed to scale to arbitrarily many repos; the array grows without schema changes.

```json
  "generator": "index-builder@v1",
  "org": "ventusltd",

    "repo": "ventusltd/globalgrid2050",
    "role": "whorl-origin",
    "status": "frozen-readonly"
  },
  "repos": [
    {
      "name": "app-solar-bess-topology-v8",

```

Design notes: `status` enumerates `live | deprecated | archived | building`; semantic-version ranges in `dataDependencies` enable pinning; `checksum` lets the hub detect drift; the top-level `canonicalSource` documents the frozen whorl. Keep the index human-diffable so the audit-first reviewer can read each change in a PR. This mirrors the hermes-registry pattern of a top-level `schemaVersion` + `generated` timestamp + a flat `entries`/`repos` array of self-describing objects.

### (d) Template-Repository Design (“per app, all dependencies pre-installed”)

`template-app` is a GitHub template repository containing, on its default branch:

```
template-app/
├── index.html                # app shell, references ./vendor/* (no CDN)
├── vendor/                    # pre-installed, version-pinned client libs
│   ├── maplibre-gl.js
│   ├── leaflet.js
│   ├── proj4.js
│   ├── papaparse.min.js
│   ├── turf.min.js
│   └── datatables.min.js
├── src/                       # app logic
├── data/                      # small bundled data or fetch config
├── app.json                   # manifest stub (feeds the master index)
├── .github/workflows/
│   ├── pages-deploy.yml       # builds + deploys to Pages (LFS-aware checkout)
│   ├── audit.yml              # audit-first: workflow_dispatch, writes report
│   └── notify-index.yml       # repository_dispatch → hub on release
├── .github/dependabot.yml     # keeps vendored libs current
├── AGENTS.md / README.md      # conventions + onboarding
└── audit/                     # committed Markdown+JSON audit reports
```

Spin-up is one command: `gh repo create ventusltd/app-<slug>-v<n> --template ventusltd/template-app --public`, or the “Use this template” button. Because a template generates a fresh single-commit history (not a fork), each app is independent with no parent link. The vendored `vendor/` directory is what makes the repo “self-contained with all dependencies pre-installed.” Dependabot handles the one downside of vendoring (staleness) by opening version-bump PRs that the founder approves under the existing audit discipline. `template-data` is analogous but ships the ETL Python scripts, YAML manifests, the `dataset.json` stub, and a tiling workflow instead of an app shell.

A note on the `pages-deploy.yml` LFS handling: GitHub Pages will not resolve LFS pointer files, so if any deployed asset is LFS-tracked the deploy Action must `actions/checkout` with `lfs: true` and publish the *resolved* binaries to the deploy branch — otherwise the site serves broken pointer text. The cleaner default is to keep browser-served assets out of LFS entirely.

### (e) Risks, Limits & Mitigations

**GitHub Pages limits (authoritative — GitHub Docs, “GitHub Pages limits”):** “Published GitHub Pages sites may be no larger than 1 GB”  and source repos have “a recommended limit of 1 GB”;  “GitHub Pages deployments will timeout if they take longer than 10 minutes”;  “a soft bandwidth limit of 100 GB per month”;  and “a soft limit of 10 builds per hour. This limit does not apply if you build and publish your site with a custom GitHub Actions workflow.”   Pages on the free tier requires public repos.

- *Mitigation:* splitting the 2 GB monolith into many sub-1-GB repos is the primary fix. Keep each app repo lean; push heavy data to data repos/object stores; deploy via Actions to dodge the 10-builds/hour cap.

**Bandwidth at “infinite” scale:** 100 GB/month is per-site soft; many spokes spread load, but a single popular heavy-data app can still exceed it. GitHub Docs note that exceeding usage may trigger throttling — “an HTTP status code of 429”   — or “a polite email from GitHub Support suggesting strategies for reducing your site’s impact on our servers, including putting a third-party content distribution network (CDN) in front of your site.” 

- *Mitigation:* serve large tiles from Cloudflare R2 — per Protomaps, “R2 is the recommended storage platform for PMTiles because it does not have bandwidth fees, only per-request fees,”  and Cloudflare’s pricing confirms “there are no charges for egress bandwidth for any storage class”  (free tier 10 GB storage + 1M Class A + 10M Class B operations/month). Keep browser-delivered facts compact (pre-computed JSON, gzip/brotli, JSONL chunking) and rely on CDN caching of immutable, versioned filenames.

**Git LFS free tier is tiny and Pages won’t serve LFS files directly.** Per GitHub Docs, each account includes 1 GiB storage + 1 GiB/month bandwidth; data packs have been replaced by metered billing (”$0.07 per GiB” storage, “$0.0875”  per GiB bandwidth).  Public clones and Actions can silently burn the bandwidth quota; once exceeded, “Git LFS support is disabled on your account until the next month.” 

- *Mitigation:* use LFS only for *source* archival of raw data, never for browser delivery; for Pages deploys, fetch LFS in the Action and publish resolved binaries; prefer GitHub Releases or an object store for very large raw files.

**PMTiles + GitHub Pages Range-request bug (decision-critical).** Per the Protomaps docs, “PMTiles archives hosted on GitHub Pages currently do not load in Firefox.” The diagnosed cause is a Firefox-specific byte-range failure: GitHub Pages returns “a 416 Range Not Satisfiable error” because Firefox alone sends an `Accept-Encoding: gzip, deflate, br, zstd, identity` header  on the range request, interacting badly with Pages’ caching (`cache-control: max-age=600`).  It is not a size or CORS issue (it appears even on ~9 MB files). Both tracking issues are confirmed **Open**: PMTiles issue #584 (opened by maintainer `bdon`, Jul 1 2025) and the underlying browser-cache issue #272 (opened Oct 20 2023).

- *Mitigation:* host PMTiles on a Range-friendly object store with proper CORS (allow `range`, `if-match`; expose `etag`) — Cloudflare R2 is Protomaps’ recommended platform. Reserve GitHub Pages for the app shell and compact JSON facts.

**Polyrepo sprawl & cross-cutting-change pain.** The well-documented downside of polyrepos: a single feature can require edits across many repos, and over-fine splitting makes shared-library changes annoying.

- *Mitigation:* strict repo-type taxonomy and prefix naming; template repos so every repo is born consistent; the master index as the always-current map; a shared-workflow repo (reusable workflows) so CI logic isn’t duplicated across dozens of repos; version-pinned data dependencies so a data change doesn’t silently break apps.

**Cross-repo automation auth.** `GITHUB_TOKEN` is scoped to its own repo and cannot trigger workflows in sibling repos (the documented error: “Resource not accessible by integration”);  cross-repo dispatch needs a PAT or GitHub App token with `repo` scope.

- *Mitigation:* store a fine-grained PAT/App token as an org secret used only by the notify-index and index-builder workflows; least-privilege scope.

**Preserving the audit-first GridBot doctrine across the federation.** The existing discipline (audit-first/apply-second, `workflow_dispatch`, Python ETL, YAML manifests, committed Markdown+JSON audit reports, founder approval) must survive federation.

- *Mitigation:* bake the audit workflow into both templates so every new repo inherits it; keep `workflow_dispatch` (manual trigger + approval) as the apply gate in each repo; have the **index-builder emit its own committed audit report** (what changed, which repos added/removed/version-bumped) so the federation itself is audited; use GitHub Environments with required reviewers for the “apply” job; treat `index.json` changes as reviewable PRs. This turns the doctrine from a single-repo practice into a federation-wide invariant.

## Recommendations

**Stage 1 — Prove the pattern on one app + one dataset (low risk, reversible).**

1. Mirror-backup the whorl repo to `archive-whorl-mirror` (`git clone --mirror`); never push to origin.
1. Stand up the hub repo, `template-app`, and `template-data`; set the custom domain.
1. Extract one dataset (`data-grid-networks`) and one app (`app-solar-bess-topology-v8`) with `git filter-repo` from a fresh clone. Vendor libs, convert that app’s map layers to PMTiles on R2, deploy both to Pages.

- *Advance when:* the extracted app is functionally identical to the monolith version and loads in Chrome **and Firefox** (the latter proves the R2/Range decision).

**Stage 2 — Build the index + automation.**
4. Define and commit the `index.json` schema; build the index-builder workflow (org enumeration via REST/GraphQL + manifest reads). Build the hub catalog UI.
5. Add `repository_dispatch` notifications and the nightly rebuild + consistency check, all emitting audit reports.

- *Advance when:* a freshly templated repo auto-appears in `index.json` within one scheduled cycle, with a committed audit trail.

**Stage 3 — Bulk migration.**
6. Extract remaining apps (the v2–v8 sandbox line, v1–v6 tracker line, price estimators, cable knowledge bases, requirements docs) and datasets in dependency order (data repos first). One repo per PR-reviewed batch.

- *Advance when:* every monolith capability is reachable from the hub and every repo is < 1 GB.

**Stage 4 — Operate & govern.**
7. Enforce naming/taxonomy via a lightweight org policy doc; enable Dependabot in templates; route all “apply” steps through Environments with required review.

**Thresholds that change the plan:**

- If an app repo approaches **1 GB** or builds exceed **10 min** → split data out or move artifacts to Releases/R2.
- If a site nears **100 GB/month** bandwidth → move its heavy assets to R2/CDN immediately.
- If LFS bandwidth nears **1 GiB/month** → stop using LFS for any browser-served file.
- If cross-repo changes become frequent and painful → consider consolidating a few over-split spokes (the polyrepo escape hatch), or introduce reusable workflows before splitting further.

## Caveats

- **Range-request fragility is the single biggest technical risk** and the reason PMTiles must not live on Pages. PMTiles issues #584 and #272 are both **Open** as of research time, and the Protomaps maintainer has reproduced the Firefox failure on the official demo — re-verify their status before relying on any Pages-hosted tiles.
- **GitHub’s free limits are “soft” but enforceable** — GitHub may throttle (HTTP 429) or email you to reduce usage; the architecture assumes good-faith static use, not commercial SaaS, which the Pages Terms of Service prohibit (“not intended for or allowed to be used as a free web-hosting service to run your online business… or any other website that is primarily directed at… facilitating commercial transactions or providing commercial software as a service”).
- **`git subtree split` vs `git filter-repo`:** subtree is fine for a single clean directory but is slow on large histories and single-branch; `filter-repo` is the general recommendation. If any app’s files were moved between directories over time, plain subtree split will lose the pre-move history — use `filter-repo` path rules in that case.
- **Vendoring trades freshness for resilience;** without Dependabot/Renovate, vendored libs go stale silently. The template must ship dependency automation.
- **Forking is deliberately *not* used for app creation** (it carries full history + parent link, and per GitHub Docs “Forking and pulling a repository counts against the parent repository’s bandwidth usage”  for LFS); templates are the correct primitive.
- **Cost figures and quotas** (metered LFS billing, R2 free-tier allowances) reflect GitHub’s and Cloudflare’s published terms at research time and can change; verify current billing before committing to any paid overage path.
