## 1. Purpose

This file exists to prevent AI or human haste from overwriting working dependencies in V6. It must be read before any new V6 change is proposed, scripted, reviewed or executed.

V6 is a modular rewrite of a working reference. Modularisation is not proof of correctness. The working behaviour must be compared against V5 before changes are made.

## 2. Binding operating rule

All V6 changes, however small or large, must be made through a named GitHub workflow or a reviewed workflow generated by a script. Direct ad hoc editing of V6 application files is not allowed during repair work.

The sequence is:

1. Read this protocol.
2. Read `uk_energy_tracking_v6/V5_V6_COMPARISON_REPORT.md`.
3. Identify one defect or one controlled repair only.
4. Create a Python repair script or deterministic patch script.
5. Create a matching GitHub Actions workflow.
6. Workflow runs the script and writes a report into `uk_energy_tracking_v6/`.
7. Workflow commits only the intended files and the repair report.
8. Maintainer tests the live page.
9. No second feature is added until the first is accepted or reverted.

## 4. Non negotiable V6 chart contract

The raw chart must show published data only. Experimental forecast layers must not contaminate the raw chart.

The current raw chart contract is:

1. 12 hour, 1 day, 7 day, 30 day, 3 month and 6 month views use full half hourly settlement data.
2. 12 month, 5 year and 10 year views use the daily aggregate file and must preserve daily high, average and low.
3. V5 is the behavioural reference unless the comparison report proves a V6 difference is intentional.
4. High, average and low values must not be hidden for visual neatness.
5. Full screen, period arrows, mobile portrait, mobile landscape and desktop must be checked after every chart repair.
6. Elexon source fields and generated daily aggregate values must remain traceable.

## 5. Forbidden repair behaviour

Do not:

1. Rewrite whole V6 files by hand when a smaller deterministic patch is possible.
2. Add a forecast, annotation or new UI feature while the raw V6 chart is still not at V5 parity.
3. Delete V5, V4 or any stable reference app.
4. Move shared datasets or change data paths without a workflow and explicit approval.
5. Hide data truth to make the chart look cleaner.
6. Patch multiple unrelated defects in one workflow.
7. Trust screenshots alone without comparing source files and data outputs.

## 6. Required repair workflow shape

Every V6 repair must use this structure:

```text
scripts/repair_v6_<short_name>.py
.github/workflows/repair_v6_<short_name>.yml
uk_energy_tracking_v6/V6_REPAIR_<SHORT_NAME>_REPORT.md
```

The Python script must:

1. Read this protocol.
2. Read the V5 V6 comparison report.
3. Read the target file or files.
4. Assert expected old text or expected structure before editing.
5. Make the smallest necessary change.
6. Assert expected new text or structure after editing.
7. Write a repair report into the V6 folder.

The workflow must:

1. Run the Python repair script.
2. Commit only the target files and the repair report.
3. Use a clear commit message.
4. Avoid broad `git add .` unless the script itself generated a manifest of touched files.
